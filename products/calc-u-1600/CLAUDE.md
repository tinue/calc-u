# Calc-U-1600

Calc-U-1600 lives in `products/calc-u-1600/` of the source repository tinue/calc-u (ADR 0002). Work happens on short branches merged into `main` (ADR 0029); a release is tagged `calc-u-1600-vX.Y.Z` (ADR 0028). The repository's `CLAUDE.md` holds the current phase and its rules; they come first.

User help is `help/` (the product parts, one file or more per chapter, `help/help.yaml`) and `library/help/` at the repository root (the shared parts), checked by `tools/help check calc-u-1600` in Frequent (`CalcU1600HelpCheck`; LIB-16) and built into the release's `Calc-U-1600-help.zip`; a user-visible change updates its chapter in the same step. Developer documents stay in `docs/developer/`.

Before removing, simplifying or "fixing" code in a review or cleanup, read `docs/background/Decisions.md`. It lists deliberate choices that look wrong at first sight. When a recurring review question gets settled, add it there.

## Test builds

All C++ builds go through the repository's root CMake project (ADR 0003; options `CALCU_PRODUCT_59`, `CALCU_PRODUCT_1600`, `CALCU_FRONTEND_QT`, `CALCU_TESTS`), the Emscripten ones too (`build/web`); this directory does not configure on its own. Run the test suite optimized: `tools/run_tests.sh` (every Frequent CTest entry of the product, `-O1`, the repository's `build/tests` tree) or the `CoreTests` target of any root tree (`-O1` in Debug). When chasing a bug — a debugger, stepping, inspecting variables — first build a full-debug tree and work there, leaving the other trees as they are:

```sh
cmake -S ../.. -B ../../build/debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCALCU_FRONTEND_QT=OFF -DCALCU_TESTS_DEBUG=ON
cmake --build ../../build/debug --target CoreTests
```

A test file registers its tests with `TEST(name)` of the repository's one runner, `library/testing/TestHarness.hpp` (ADR 0038; `CHECK`, `CHECK_EQ`, `SKIP_UNLESS` for a missing ROM); there is no list of tests to keep. `tools/run_tests.sh <substring>` runs the tests whose name contains it, in every runner program of the product (`CoreTests`, the two session runners, DAP, help). Every CTest entry is in a test group (ADR 0031; `docs/test-groups.md` at the repository root): a tree has the Frequent group (`CoreTests`, `CalcU1600SessionTests` and `CalcU1600AppSessionTests` (the tests on `app/tests/SessionFixture.hpp` of `tests/` and of `app/tests/`, split off by CMake so that the three run side by side), `CalcU1600DapTests` (the DAP server's cases, `tests/dap/`), `CalcU1600HelpTests` (`tests/help/`), `CalcU1600HelpCheck`, `CalcU1600HelpBuild` (the help, LIB-16), `calcu_preset_check.CalcU1600Presets`, `calcu_preset_check.CalcU1600Templates`; ≤ 60 s), and with `-DCALCU_TESTS_LONGER=ON` / `-DCALCU_TESTS_CHECKPOINT=ON` also the Longer and Checkpoint ones (`ctest -L longer`; among them `CalcU1600HarnessTests`, `tests/harness/`: the `c1600` commands and the harness entry, each test on a `calcu` run; `CalcU1600MachineStateTests`, `tests/machine_state_tests.cpp`: the machine state).

## Harness

`calcu` is the family's harness (LIB-11, `features/LIB-11-harness/` at the repository root): the product without a window, on the library's app session with the product's app layer `app/SharpAppPart` as the frontends host it (LIB-11 D-6, `app/HarnessProduct.cpp`: built in `prepare()` on the run's settings and folders), in emulated time only, so two runs give the same replies. It replaced `pc1500_cli`, `pc1600_cli` and the probes in M-51 (LIB-11 AC-18: every function of theirs is a command below). Build the target `calcu` of a root tree (`cmake --build ../../build/tests --target calcu`; the program is `build/tests/library/harness/cli/calcu`). It finds the ROMs in `roms/` through the product's lookup (`sharp::lookUpRoms`), the module definitions (`*.module.yaml`) in `frontends/qt6/resources/cards/` (and the ROM set's `CE-502B.module.yaml`), the host drive's ROM in `firmware/pc1600-hostdrive/`, the bundled presets in `examples/` (`examples/bundle.yaml`), and starts the startup model (the PC-1500A under the default settings) cold booted, at key readiness (LIB-18; its machines are `app/SharpProductMachines`). Scratch output goes to `headless/`.

- One-shot: `calcu --product c1600 wait 2s then display-text then ticks` (commands parted by `then`; exit status 0, 1 at the first refusal, 2 when it cannot start).
- `calcu --product c1600 serve`: one command per line on standard input, one reply per line (`done`, `done <n>` and n lines, `refused: <reason>`); `--json` gives one object `{"done","result","reason"}` per reply. From Python: `library/harness/python/calcu_serve.py`.
- First commands: `wait <2s|500ms>`, `key-down`/`key-up <key ID>`, `display-text` (rows of text, the cell under the cursor read as the character the ROM saved there (`app/LcdTextPart`), `indicators:`, `not text:`, or `display off`), `display`, `state <topic>`, `capabilities`, `ticks`, `audio <file.wav>`, `quit` (`calcu --help`).
- Machine control (LIB-18): `model <PC-1500|PC-1500A|PC-1600>`, `variant <A01|A03|A04|New|Old>`, `attach <place> <peripheral>[:<variant>]` (`attach printer CE-1600P:old`), `detach <place>`, `reset`, `cold-boot`, `power-cycle`; each replies when the machine is ready for keys again. No settings or save folder of yours is touched unless `--settings`, `--save-folder`, `--output-folder` name them.
- Typing (LIB-5): `key <name> ...` (key IDs and `break` for `on`, any case; replies when the last key is up) and `type <text>` (the text and ENTER; replies when ENTER is up). Neither waits until the machine is idle: `wait` does.
- A debugger (C1600-3): `calcu --product c1600 serve --dap <port>`: VS Code (or `tools/dap_smoke.py --harness`) attaches to the machine without a window; while the DAP session has the machine running, emulated time passes unpaced (no wall clock); `c1600/quit` ends the run. A port outside 1024 to 65535 ends the start with exit status 2.
- Debugger (LIB-10): `targets`, `registers`, `pause`, `step`, `step-over`, `step-out`, `resume`, `break`, `watch`, `peek`/`poke` (spaces `me0`, `me1`, `me1-written` of the LH5801/LH5803, `memory`, `io`, `io-written` of the SC7852; `bank=`, `vbank=`), `history`, `disassemble`, `trace <file>|off` (into `--output-folder`), `symbols`, `pause-on-start cpu`.
- Paper (LIB-8): `paper marks|png <path>|copy|cut [CE-150|CE-1600P]`, `cut-paper`.
- Program files (C1600-2): `c1600 file-kind <file>` (what it is; a WAV's files), `c1600 load-basic <file> [<n>]`, `c1600 type-basic <file>` (typed through the ROM's editor; program mode first), `c1600 load-code <file> [<n>] [address=<a>] [length=<l>] [cpu=<lh5803|z80>] [run]` (the reply: range, area, bank, NEW, the starting command, warnings). Refusals are `refused: <file>: <reason>`.
- Opening a file (LIB-13): `open <path>` opens it as a frontend's drop does: a preset by its extension (`.pc1500`, `.pc1500a`, `.pc1600`) or its `model:` line, a medium (`.module.yaml`, `.floppy.yaml`, `.cassette.yaml`) into its place from where it lies, a BASIC or machine-code program (`app/SharpFileKinds`) loaded at once (a WAV's first file; headerless code is refused, it needs an address). The reply: `preset|medium|file-kind <name> [<place or kind>]`, or `refused: <sentence>`.
- Presets (LIB-6, C1600-4): `preset <file>|examples:<path>` (format 2 only; version 1 is refused with the hint), `check-preset <file>…`, `preset-list`, `wait` without a duration (until idle), `expect`/`not-expect` (text in one line of `display-text`, or `/regex/`), `screenshot <name>` (Copy Screen's picture, into `--output-folder`), and the steps as commands. The product's keys and sections are in `app/SharpPresetKeys` (`program:`, `host-drive:`, `slot-N-rom:`, `bus-rom:`, `debug:`), its rules in `app/SharpPresetRules`.
- Media (LIB-7): `media` (the topic: the modules, disks and cassettes, templates and saved instances, what each place holds), `media import <file>`, `media export <kind> <name> <path>`, `media delete <kind> <name>`; the steps as commands: `floppy { name: Formatted, side: 1 }`, `cassette { file: x.cassette.yaml }`, `eject floppy|cassette`, `saveas { place: slot-1, as: live, name: Mine }`. Kinds `battery-backed-module` (`.module.yaml`, `format: memory-module`), `floppy-disk` (`.floppy.yaml`, version 2, sides 0 and 1), `cassette` (`.cassette.yaml`, `format: cassette`, with its WAV, in the cassette folder; the media place `cassette-recorder`); the codecs in `app/SharpMediaKinds`, the places in `core/Machine/SharpMediaPlaces`. The run's save folder is empty unless `--save-folder` names one.
- Product commands (C1600-5, `app/SharpHarnessCommands`): `c1600 dump-basic` (the BASIC pointers and the program area, the CLIs' `--dump-basic` lines), `c1600 inspect <view>` (an INSPECTOR view: `pointers`, `inventory`, `lh`, `basic`, `physical`, `dump-basic`, `dump-ml`, `z80`, `programs`, `disks`, `dump-s1`, `dump-s2`, `dump-disk-s1`, `dump-disk-s2`), `c1600 cassette record <file.wav>` (a new cassette whose recording is written to the WAV at each motor stop and at eject) and `c1600 cassette status`, `c1600 serial ce158|rs232c feed <file> [hold=<n>]|capture <file>|link|report` (`app/SerialScripts`: the feed one byte per character time in emulated ticks; no serial port file unless `link`), `c1600 host-drive <folder>|off` (PC-1600), `c1600 call <target> <address> [timeout=<d>]` (a paused machine runs a routine until it returns: `c1600.routine-call` and LIB-10's step-out). Memory dumps are `peek … [file=<file>]` (LIB-10).
- Machine state (LIB-11 AC-24, C1600-5 AC-13): `state-save <file>` writes the whole machine with its plugged peripherals and their media (the processors, all memory with the banks, the chips and clocks, the modules, the CE-150's and CE-1600P's mechanism, the CE-158, the disk with its side, the cassette with its sound and position, the host drive's open handles but not its folder); `state-restore <file>` continues from it, in the same run or another one set up with the same model, variant and peripherals, and is refused (nothing changes) otherwise. The form is internal: `core/Machine/StateRecords.hpp` (tagged records; each part's fields in its `stateIo` template), `SharpMachine::saveState`/`restoreState`, the kind on the main processor. Not in it, as the session keeps them: what LIB-7 believes a media place holds, the `cassette record` path, the paper, the serial queues, the debugger's breakpoints and history.

## Core, app layer, frontends

Three layers (docs/developer/App-Layer.md): `core/` is the hardware, `app/` the app layer, all app logic that isn't drawing (namespace `cu1600`, as Calc-U-59's is `cu59`), `frontends/qt6/app/` the desktop GUI, `frontends/web/` the WebAssembly browser GUI.

- Non-GUI logic goes in `app/` (or `core/`), never in `frontends/qt6/app/`; Qt classes translate types and show what the app layer decides.
- Above `core/`, the machine is only a `calcu::machine::Machine` (C1600-1): built with `calcu::machine::build(sharp::sharpCatalogue(), SharpMachineBuilder, request)`; Sharp-only functions are capabilities (`c1600.*` kinds, `core/Machine/SharpProductKinds.hpp`); the adapters of `core/Machine/LegacyCalls.hpp` went in M-51 (the adapter check of plan §1; `tools/check_no_old_tools.cmake`). Every ROM image comes from the one ROM lookup at the start (`sharp::lookUpRoms`, `core/Machine/SharpRoms.hpp`, LIB-12) and its `calcu::roms::RomSet`; nothing else reads a ROM file (the CTest `CalcU1600NoOwnRomLookup`; the one exception is the host-drive ROM, `sharp::readHostDriveRom`). Descriptors and kinds live in `core/Machine/`. Never include or name `PC1500Machine`/`PC1600Machine` in `app/`, `frontends/`, `tools/` or `dev/`: the CTest `CalcU1600MachineIncludeCheck` (`tools/check_machine_includes.sh`, Frequent and CI) fails.
- Core and app layer: portable C++20, standard library only, single-threaded, never blocking; the machines hold no lock (ADR 0009). Long machine work is an operation of the library's session (`calcu::sessions::Task`, `OperationContext::run`); coroutine parameters by value. `core/` holds only what the products run: the old typers and their `namespace job` forwarder are the tests' (`tests/support/`: the golden runs' and C1600-2 AC-7's reference typer, compiled into `CoreTests` only).
- Every frontend hosts the library's app session (`library/sessions/`, LIB-3) with the product's part `app/SharpAppPart` (the library's parts it brings: typing, peripherals, presets, startup, the loaders, paper, debugger, media (LIB-7's `MediaPart`: the topic `media`, `media.choose`, `media.turn`, `media.name-and-save`, `media.start-new`, autosave; `app/SharpMediaKinds`); LIB-13's open part: the command `open` of every way a file reaches the product, the product's file kinds in `app/SharpFileKinds`; the product commands `c1600.mount-host-drive`, `c1600.ce1600p-variant`, `app/SharpTopics.hpp`; LIB-4's `ControlPart` with the product's rules `app/SharpControlRules`, the topic `control-state`, first in the one order of the parts that `LibraryParts::sessionParts` gives (`SharpAppPart::sessionParts(host, after)`)) and talks to it by messages: the start, the model and variant switches, attach, detach, Reset and Cold boot are LIB-18's commands (`start`, `model`, `variant`, `attach`, `detach`, `reset`, `cold-boot`), a preset is LIB-6's `load-preset {ref}`; pacing is the library's (LIB-17, `app/PacingProfiles`). The product writes no session class of its own (CTest `CalcU1600NoOwnSession`), and an operation never runs to its end on a frontend's thread: it runs in parts, one per host call. `app/SharpSession` (`makeSharpSession`) builds the session for a native host, which talks to it through the library's `calcu::sessions::Listener` (the tests' `app/tests/SessionFixture.hpp`, `tools/wasm_smoke`). Both frontends are put together from LIB-14's shell (M-49) with the product's data `app/SharpShellProduct` (items, labels, the hit map, the settings spec): the Qt6 window is a `calcu::qt6::Shell` over the `calcu::qt6::SessionHost` that `MachineController` (the product's glue: the session with LIB-14's `SettingsPart`, the sound feed, the DAP server's socket `frontends/qt6/app/debug/DapSocket`) makes; the Web page is the React set's shell over the session `frontends/web/bindings.cpp` builds for the library's worker (with `SettingsPart` and `app/SharpWebPart`, the product's requests). Models are `ModelId`s (`shared::Model` is gone). In development and test builds (`CALCU_ATTACH`) the Qt6 app offers harness attach (`--attach-port N`, else 59059); `--shots` (the screenshot scenarios, `docs/developer/screenshots/README.md`) and `--pacing-probe` are its clients and step the machine only through it. Keys and typing go through the library's typing engine (LIB-5; the profiles and keyboard maps in `app/SharpTyping`, the frontends send `host-key-down`, `screen-key-down`, `paste`, ...); the debugger is the library's `DebuggerPart` (LIB-10; `app/SharpDebuggerSetup`, the targets in `core/Debug/SharpDebugging`) and the paper the library's `PaperPart` (LIB-8; `app/SharpPrinters`, `core/Connector/PlotterPaperOutput.hpp`); the DAP server (C1600-3) is `app/dap/` (`DapPart` among `SharpAppPart`'s parts) on every native host: the Qt6 frontend gives it its socket, the harness serves it with `serve --dap`, the Web has none.
- A change to `core/` or `app/` passes `tools/run_tests.sh` and `tools/build_wasm_check.sh`, and the Qt app builds; a change the web client sees also passes `frontends/web/build.sh` + `frontends/web/run-tests.sh`.
