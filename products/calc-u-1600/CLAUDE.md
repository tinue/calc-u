# Calc-U-1600

The product rules on top of the repository's `CLAUDE.md`.

User help is `help/` (the product parts, `help/help.yaml`) and `library/help/` at the repository root (the shared parts), checked by `tools/help check calc-u-1600` (`CalcU1600HelpCheck`, Frequent) and built into the release's `Calc-U-1600-help.zip`. Developer documents stay in `docs/developer/`.

## Test builds

All C++ builds go through the repository's root CMake project (options `CALCU_PRODUCT_59`, `CALCU_PRODUCT_1600`, `CALCU_FRONTEND_QT`, `CALCU_TESTS`), the Emscripten ones too (`build/web`); this directory does not configure on its own. Run the test suite optimized: `../../tools/run_tests.sh calc-u-1600` (the repository's one test script: every Frequent CTest entry of the product, `-O1`, the repository's `build/tests` tree) or the `CoreTests` target of any root tree (`-O1` in Debug). When chasing a bug — a debugger, stepping, inspecting variables — first build a full-debug tree and work there, leaving the other trees as they are:

```sh
cmake -S ../.. -B ../../build/debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCALCU_FRONTEND_QT=OFF -DCALCU_TESTS_DEBUG=ON
cmake --build ../../build/debug --target CoreTests
```

A test file registers its tests with `TEST(name)` of the repository's one runner, `library/testing/TestHarness.hpp` (`CHECK`, `CHECK_EQ`, `SKIP_UNLESS` for a missing ROM); there is no list of tests to keep. `../../tools/run_tests.sh calc-u-1600 <substring>` runs the tests whose name contains it, in every runner program of the product (`CoreTests`, the two session runners, DAP, help). Every CTest entry is in a test group (`docs/test-groups.md` at the repository root): a tree has the Frequent group (`CoreTests`, `CalcU1600SessionTests` and `CalcU1600AppSessionTests` (the tests on `app/tests/SessionFixture.hpp` of `tests/` and of `app/tests/`, split off by CMake so that the three run side by side), `CalcU1600DapTests` (the DAP server's cases, `tests/dap/`), `CalcU1600HelpTests` (`tests/help/`), `CalcU1600HelpCheck`, `CalcU1600HelpBuild` (the help), `calcu_preset_check.CalcU1600Presets`, `calcu_preset_check.CalcU1600Templates`; ≤ 60 s), and with `-DCALCU_TESTS_LONGER=ON` / `-DCALCU_TESTS_CHECKPOINT=ON` also the Longer and Checkpoint ones (`ctest -L longer`; among them `CalcU1600HarnessTests`, `tests/harness/`: the `c1600` commands and the harness entry, each test on a `calcu` run; `CalcU1600MachineStateTests`, `tests/machine_state_tests.cpp`: the machine state).

## Harness

`calcu --product c1600` is the product without a window, in emulated time only, so two runs give the same replies. Build the target `calcu` of a root tree (`cmake --build ../../build/tests --target calcu`; the program is `build/tests/library/harness/cli/calcu`). It finds the ROMs in `roms/`, the module definitions in `frontends/qt6/resources/cards/` (and the ROM set's `CE-502B.module.yaml`), the host drive's ROM in `firmware/pc1600-hostdrive/` and the bundled presets in `examples/`; scratch output goes to `headless/`. The common commands, replies and options are in `docs/formats/harness.md` (repository root), the `c1600` commands in `docs/developer/Harness.md`, the DAP server (`serve --dap <port>`) in `docs/developer/DAP.md`. The pytest driver on it is `tools/machine/`.

## Core, app layer, frontends

Three layers (docs/developer/App-Layer.md): `core/` is the hardware, `app/` the app layer, all app logic that isn't drawing (namespace `cu1600`, as Calc-U-59's is `cu59`), `frontends/qt6/app/` the desktop GUI, `frontends/web/` the WebAssembly browser GUI.

- Non-GUI logic goes in `app/` (or `core/`), never in `frontends/qt6/app/`; Qt classes translate types and show what the app layer decides.
- Above `core/`, the machine is only a `calcu::machine::Machine`: built with `calcu::machine::build(sharp::sharpCatalogue(), SharpMachineBuilder, request)`; Sharp-only functions are capabilities (`c1600.*` kinds, `core/Machine/SharpProductKinds.hpp`). Every ROM image comes from the one ROM lookup at the start (`sharp::lookUpRoms`, `core/Machine/SharpRoms.hpp`) and its `calcu::roms::RomSet`; nothing else reads a ROM file (the CTest `CalcU1600NoOwnRomLookup`; the one exception is the host-drive ROM, `sharp::readHostDriveRom`). Descriptors and kinds live in `core/Machine/`. Never include or name `PC1500Machine`/`PC1600Machine` in `app/`, `frontends/`, `tools/` or `dev/`: the CTest `CalcU1600MachineIncludeCheck` (`tools/check_machine_includes.sh`, Frequent and CI) fails.
- Core and app layer: portable C++20, standard library only, single-threaded, never blocking; the machines hold no lock. Long machine work is an operation of the library's session (`calcu::sessions::Task`, `OperationContext::run`); coroutine parameters by value. `core/` holds only what the products run: the old typers and their `namespace job` forwarder are the tests' (`tests/support/`: the golden runs' and the program-file tests' reference typer, compiled into `CoreTests` only).
- Every frontend hosts the library's app session (`library/sessions/`) with the product's part `app/SharpAppPart` (the library's parts it brings: typing, peripherals, presets, startup, the loaders, paper, debugger, media (the library's `MediaPart`: the topic `media`, `media.choose`, `media.turn`, `media.name-and-save`, `media.start-new`, autosave; `app/SharpMediaKinds`); the open part: the command `open` of every way a file reaches the product, the product's file kinds in `app/SharpFileKinds`; the product commands `c1600.mount-host-drive`, `c1600.ce1600p-variant`, `app/SharpTopics.hpp`; the `ControlPart` with the product's rules `app/SharpControlRules`, the topic `control-state`, first in the one order of the parts that `LibraryParts::sessionParts` gives (`SharpAppPart::sessionParts(host, after)`)) and talks to it by messages: the start, the model and variant switches, attach, detach, Reset and Cold boot are the library's commands (`start`, `model`, `variant`, `attach`, `detach`, `reset`, `cold-boot`), a preset is `load-preset {ref}`; pacing is the library's (`app/PacingProfiles`). The product writes no session class of its own (CTest `CalcU1600NoOwnSession`), and an operation never runs to its end on a frontend's thread: it runs in parts, one per host call. `app/SharpSession` (`makeSharpSession`) builds the session for a native host, which talks to it through the library's `calcu::sessions::Listener` (the tests' `app/tests/SessionFixture.hpp`, `tools/wasm_smoke`). Both frontends are put together from the library's shell with the product's data `app/SharpShellProduct` (items, labels, the hit map, the settings spec): the Qt6 window is a `calcu::qt6::Shell` over the `calcu::qt6::SessionHost` that `MachineController` (the product's glue: the session with the library's `SettingsPart`, the sound feed, the DAP server's socket `frontends/qt6/app/debug/DapSocket`) makes; the Web page is the React set's shell over the session `frontends/web/bindings.cpp` builds for the library's worker (with `SettingsPart` and `app/SharpWebPart`, the product's requests). Models are `ModelId`s. In development and test builds (`CALCU_ATTACH`) the Qt6 app offers harness attach (`--attach-port N`, else 59059); `--shots` (the screenshot scenarios, `docs/developer/screenshots/README.md`) and `--pacing-probe` are its clients and step the machine only through it. Keys and typing go through the library's typing engine (the profiles and keyboard maps in `app/SharpTyping`, the frontends send `host-key-down`, `screen-key-down`, `paste`, ...); the debugger is the library's `DebuggerPart` (`app/SharpDebuggerSetup`, the targets in `core/Debug/SharpDebugging`) and the paper the library's `PaperPart` (`app/SharpPrinters`, `core/Connector/PlotterPaperOutput.hpp`); the DAP server is `app/dap/` (`DapPart` among `SharpAppPart`'s parts) on every native host: the Qt6 frontend gives it its socket, the harness serves it with `serve --dap`, the Web has none.
- A change to `core/` or `app/` passes `../../tools/run_tests.sh calc-u-1600` and `tools/build_wasm_check.sh`, and the Qt app builds; a change the web client sees also passes `frontends/web/build.sh` + `frontends/web/run-tests.sh`.
