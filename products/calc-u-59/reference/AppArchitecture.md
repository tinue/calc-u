# App and Bridge Architecture

> **Provenance notice.** This document was generated by an AI (Claude) from
> human-authored specifications and source code.  The app was built through
> iterative human testing and feedback; the AI produced code and documentation
> to meet those specifications.

The Swift app (`frontends/swift/App/`, `frontends/swift/Bridge/`) for macOS and iOS/iPadOS. It is a renderer
over `app/SessionController`; everything that isn't drawing — the run
loop, keys, presets, cards, the printer strip, the debugger, the rules the
views draw with — is in `app/` and documented in `SharedArchitecture.md`.

---

## Layer Overview

```
CalcU59App                    (Calc-U-59App.swift: scene, background/active, macOS Settings + About)
└─ CalculatorView             (adaptive layout, toolbar, card bar, file importer, alerts)
    ├─ KeyboardView           (calculator art, hit test, LED + cue-card overlays, physical keys)
    │   ├─ LEDDisplayView
    │   └─ CueCardView
    ├─ PrinterView            (paper strip, PRINT / T / ADV, copy, cut)
    ├─ CardPickerView         (fit card / fit fresh card sheet)
    ├─ DebugView              (CALCULATOR / CPU / LOG tabs)
    │   ├─ LiveDebugView      (CALCULATOR)
    │   ├─ CPUInspectorView   (CPU, with the ROM heatmap) + ASMDebugContent
    │   └─ StaticDebugContent (LOG)
    └─ SettingsView

EmulatorViewModel (@Observable, main thread)
├─ TIAppSession               (frontends/swift/Bridge/ → app/SessionThread, app/TIAppPart)
├─ PlatformForwarder          (TIPlatform: files, trace location, settings, alerts, changes)
└─ displayTimer               (60 Hz Timer → controller.tick())
```

## Threading

| Thread | What runs there |
|---|---|
| Main | SwiftUI, every `TIAppSession` call (each posts a command and returns at once), `SessionDelegate` callbacks, all `@Observable` writes |
| Session thread (`cu59::SessionThread`) | The app session: built, called about 60 times a second, destroyed there; the machine, the presets, the card and `ti58c.mem` files (through `NSFileCoordinator`) — C59-5 |
| Attach I/O thread (Debug, macOS and simulator) | `calcu::harness::AttachEndpoint`: the socket on 127.0.0.1; lines go to the session thread |
| Global utility queue | `CardStorage.warmUp()` before the session is made — `url(forUbiquityContainerIdentifier:)` blocks and returns nil on the main thread |

The view model holds an App Nap activity token for its lifetime, so macOS
never stalls the session thread while the window is covered (C59-5 AC-9).

### Messages, not a refresh timer

There is no display timer. The session thread wakes the main thread once
per batch of messages (`dispatch_async`); `TIAppSession` keeps the last
message of each topic and tells the view model which topics changed
(`TIAppSessionDelegate.changed(_:)`, `TIChange`). `apply(_:)` reads only
those and assigns a property only when it differs, because `@Observable`
notifies on equal writes too.

On `.background` the app sends suspend (`suspend(completion:)`: carried out
— the TI-58C's memory written — then the thread stops calling; on iOS inside
a background task); on `.active` it sends continue. A debug freeze survives.

### Harness attach (Debug)

A Debug build for macOS or the simulator opens its session to the harness
on 127.0.0.1, the port of the launch argument `--attach-port N`, else
59059 (`openAttach(withArguments:)`); `calcu attach [--port N]` on the Mac
drives it, and `Calc-U-59UITests/HarnessClient.swift` from an XCUITest.
Only the Debug configuration has `com.apple.security.network.server`
(`Calc-U-59-Debug.entitlements`); Release and device builds have no attach
(C59-5 AC-13).

## Build

Xcode compiles only Swift and the bridge (`frontends/swift/Bridge/`). The
C++ below them, the library, `core/` and `app/`, comes as
`CalcU59.xcframework` (ADR 0013): the project's aggregate target
`CalcU59Core`, which the app depends on, runs
`frontends/swift/build_xcframework.sh`, which builds it with the
repository's root CMake project for macOS, iOS devices and the iOS
simulator into `build/xcframework-59/` (Release or Debug, as the Xcode
build). So every Xcode build is built from the current sources; without
CMake and Ninja the build stops with an error. The bridge includes the
headers from the XCFramework (`<calcu59/app/…>`, `<calcu59/core/…>`).
`frontends/swift/check_xcode_project.sh` (CTest, Frequent) fails when the
project takes in a C++ source or the bridge includes from the source
tree.

## Bridge Layer

The wrappers translate types only. `frontends/swift/Bridge/Calc-U-59-Bridging-Header.h`
imports the public ones.

| Wrapper | Wraps |
|---|---|
| `TIAppSession.{h,mm}` | The app session on `cu59::SessionThread`: commands (`c59.*`) out, messages in on the main thread (the last of each topic kept); `TIAppSessionDelegate` (alerts, `DebugPanel:`, diagnostics, `changed`), `TISessionStart`, `TIRomSet`; the coordinated card files (`cu59::FileIO`); value objects `TILiveDebugSnapshot`, `TIStepEntry`, `TIRegEntry`, `TIInspectorEntry`, `TIPrinterLine`, built when Swift reads them |
| `TISharedTables.{h,mm}` | `KeyboardMap`, `SevenSegment`, `PrinterFont` (font rows), `KeyboardLayout`, `KeyIds` |
| `TIViewRules.{h,mm}` | `CueCard` (spans, geometry, inks), `LedGeometry`, `PrinterFont` (`PrinterGeometry`), `RomHeatmap`, `ModuleImage` (program source), `DebugText` (incl. the iOS `mobileLayout`, `mobilePrinterWidth`, `compactPrinterBar`, `mobileTopMargin`) |
| `TIFileFormats.{h,mm}` | `TICueCard`, card file names (`CardFile`), `cuecards.txt` module list (`ModuleCatalog`) |
| `TISettings.{h,mm}` | `Settings` (`app/Settings.hpp`) over a `calcu::settings::SettingsFile`; the trace folder from `calcu::settings::Paths` |
| `TITypes.h` | `TIDisplaySnapshot` (mirrors `LedFrame`: the glyph's segments A–G and brightness 0–255 per digit and decimal point) and `TICpuFrame` (mirrors `CpuFrame`) |
| `BridgeConvert.h` | ObjC++-only: string / data conversions; `static_assert`s that `TICpuFrame` matches `CpuFrame` field for field, so a frame converts with one `memcpy` |
| `TIFileFormats+Cpp.h` | ObjC++-only: `TICueCard` ↔ `CueCardContent` |

Never import the two ObjC++-only headers from the bridging header.

## Swift-specific details

**Keys.** `KeyboardView` hit-tests in normalised canvas coordinates and calls
`pressKey(row:col:)` with the 0-based grid position; the view model converts
it with `TISharedTables.matrixCode(row:col:)`. On iOS, key touches go through
`UIKitTouchTracker`; macOS keeps `DragGesture(minimumDistance: 0)`.
Physical keys (macOS only) go through `PhysicalKeyboardModifier`, which
subscribes to `.down` and `.up` only (dropping auto-repeat) and releases the
held key when focus is lost. Mapping, timing and focus rules:
`SharedArchitecture.md` § "Physical Keyboard Mapping".

**LED.** `LEDDisplayView` draws each cell in a `Canvas` with the shared
segments and shear, the glow and bloom as blurred copies under the crisp
fill, each at the cell's `LedFrame` brightness. Rules:
`SharedArchitecture.md` § "LED Display Rendering".

**Cue card.** `CueCardView` places the artwork `Image(template)`, then text
at the frames and font sizes `TIViewRules` returns, with `.lineLimit(1)`.
Rules: `SharedArchitecture.md` § "Cue Card Rendering". A press on the card goes
first to `tapCard` (`KeyboardView`), and `CueCardView` draws the side being read
from `litCardCorner`: `SharedArchitecture.md` § "Card Reader Flow".

**Printer.** Dot view (`PrinterDotLine`, PC-100C proportions from
`TIViewRules`) or selectable text. Copy renders the strip with
`ImageRenderer` at the shared copy scale and puts text plus the image on the
pasteboard (macOS: `NSImage`; iOS: PNG). Cut copies, then clears the strip;
`printerClearID` resets the text view's identity to drop a selection.

**Storage.** Cards and `ti58c.mem` live in the `CardStorage` folder (iCloud
Documents when available); reading `ti58c.mem`, and reading and writing cards,
go through `NSFileCoordinator`. Traces go to the trace location from Settings: Local
(`~/Library/Application Support/Calc-U-59`), iCloud (the card folder) or a
custom folder (macOS, security-scoped bookmark).
