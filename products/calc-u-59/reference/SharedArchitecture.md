# Shared C++ Layer (`app/`)

> **Provenance notice.** This document was generated by an AI (Claude) while
> moving the Swift app's non-GUI logic into `app/` and building the Qt6
> app on it. Like the other `reference/*.md` files it is best-effort and
> correct as of writing — the code wins where they disagree.

`app/` holds everything the frontends need that is neither hardware
emulation nor drawing. It sits between `core/` (the emulated hardware, see
`CoreArchitecture.md`) and the three GUIs — the two apps and the web client
(`WebClient.md`):

```
frontends/swift/App/ (SwiftUI) ── frontends/swift/Bridge/ (ObjC++) ─────────┐
frontends/qt6/app/ (Qt Widgets) ──────────────────────┼── app/ (C++20, std only) ── core/
frontends/web/ (React) ── frontends/web/bindings.cpp ───────────┘   (WebAssembly, no threads)
```

- **C++20, standard library only** (ADR 0005) — no Foundation, no Qt, no
  iCloud. CMake builds it as C++20, the Xcode project as gnu++20.
- **No locations.** `app/` never resolves where files live: it takes paths
  (`std::filesystem::path`), and ROM files only through the library's ROM
  lookup over a `calcu::roms::Bundle` the frontend makes (Swift: the
  bundle's resource folder; Qt: the `:/roms/` qrc, `QtResourceBundle`; Web:
  `/roms` in Emscripten's file system; tools and tests: `roms/`).
- **One thread.** Everything runs on the app session's thread; only
  `SessionThread` (the Swift frontend's host adapter) has a lock.
- **Namespace `cu59`.** Headers include Core relatively (`../Core/...`).

The Qt app calls `app/` directly. The Swift app goes through the ObjC++
wrappers in `frontends/swift/Bridge/`, which only translate types (`AppArchitecture.md`
§ "Bridge Layer").

## The app session (`TIAppPart`)

Every frontend hosts the library's app session (`calcu::sessions::AppSession`,
LIB-3) made by `cu59::makeAppSession` (`app/TIAppPart.hpp`): Swift and Qt6
since M-33, the Web since M-34 (LIB-15: `frontends/web/bindings.cpp` makes it
for the library's Web Worker host, with `TIWebPart` behind it). The session
holds the machine session (the machine, LIB-17's pacer with the TI profiles
of `app/PacingProfiles.hpp`) and Calc-U-59's part, `cu59::TIAppPart`. A
frontend sends commands (`cu59::commands`, `c59.*`, and the library's
`speed`, `suspend`, `continue`, …) and gets messages: the library's topics
(`display`, `busy`, `notices`, `log`) and the interim `c59.*` topics
(`c59.model`, `c59.led`, `c59.printer`, `c59.card-reader`, `c59.run-state`,
`c59.debug.*`, …; each the snapshot of one of 2.3.0's change flags, until
the feature that owns it, LIB-3 59 design §5). Qt6 calls the session on its
GUI thread, Swift on `cu59::SessionThread`, the Web in its worker (§ "Threads");
each talks to it through the library's `calcu::sessions::Listener`. The
session owns the part (`AppSessionSetup::owned`) and lets it go first.

`TIAppPart` holds the flows all GUIs share (2.3.0's `SessionController`,
taken apart in M-34): it owns the `EmulatorSession` (rebuilt on a model
switch) and the `DebugModel`, and runs starting and switching machines,
presets (an operation, LIB-3 AC-32), the TI-58C memory file, the card
reader, the printer strip, the cue card shown, freeze and step, traces,
the ASM overlay and the LOG tab. The `EmulatorSession` hands its machine to
the machine session; its freeze checks run inside each slice's advance
(`EmulatorSession::advanceHosted`, the `TIFreezeGate`), its key sequencer at
each slice end with the slice's wall time (`TIKeySequencerHook`), and a
frozen machine pauses the machine session. An error is a notice ("title:
message"), a diagnostic a log line, the card and `ti58c.mem` files go
through `TIFileAccess` in the save folder; what the `EmulatorSession`
reports waits in the part's queue and runs on the session's thread after
the call.

### The 60 Hz frame

After each host call (`TIAppPart::afterCall`):

1. **Frame** (`FrameSampler`): each position's glyph and brightness
   (`DisplayPov`), the C indicator's opacity (it follows the core's drive at
   once, holding only a single dark frame), printer text and dot lines, core
   log lines, and card auto-eject (the core executed `CRD_OFF`; written data
   is saved).
2. **Debugger** (`DebugModel::tick`): the CALCULATOR snapshot while its panel
   shows; the CPU history and heatmap while the CPU panel shows.
3. **Traces**: the core's trace ring drained into the open writers.
4. **Slower checks**: the cue card's library program (2 Hz), the LOG text
   (1 Hz), the TI-58C persist (0.5 s after a batch ran).

Then only the interim topics of what changed are published.

## Threads

The app layer has no thread of its own but one host adapter:

| Frontend | Where the session runs |
|---|---|
| Swift | `cu59::SessionThread` (`app/SessionThread.*`): builds, calls about 60 times a second and destroys the session on one thread (QoS user-initiated). Posts in one FIFO, messages out in one FIFO to the main thread, one wake per batch (C59-5). In Debug builds for macOS and the simulator it also hosts harness attach (`library/harness/attach/`) |
| Qt6 | the GUI thread: a 60 Hz `QTimer` calls the session |
| Web | the library's Web Worker (`library/web/src/worker.js`): a 60 Hz `setInterval` calls the session through the library's `WorkerHost` (LIB-15) |

Nothing else in the app layer locks (ADR 0009): `EmulatorSession`,
`TIAppPart`, `KeySequencer`, `FreezeController` and `TraceWriter` are
single-threaded.

### Key input

`KeySequencer` scripts and taps are resumable tasks that say when they next
want to run; the `EmulatorSession` advances them at the end of every slice
of the machine session, at the time the slice was due, so a 100 ms hold
spans several slices and the scan-loop wait is checked at each boundary;
with no slice (frozen), at the time of the call.

The session owns the debugger's freeze state and the core's trace flags.
Freeze, step and their threading: `DebugAPI.md` § "Freeze / Step Controls".
Core locking: `CoreArchitecture.md` § "Threading Model".

## Emulation Loop and Timing

Every frontend (Swift and Qt6 since M-33, the Web since M-34): LIB-17's pacer in the machine session, with the TI
profiles (`app/PacingProfiles.hpp`): a fixed 20 ms slice of the model's
tick rate, jittered slice ends (the TI-58's error blink, AC-17), and full
speed paced at regular speed while the machine waits for input (key
readiness, or on the TI-59 a `Write` waiting for a card; a printer wait
does not count). A call drops a lag over 100 ms; full speed runs at most
14 ms of host time per call. The long-run rate is exact (LIB-17 AC-18:
0.13 % / 0.10 % faster than 2.3.0 on the TI-59 / TI-58C, ledger 59-33).

`step()` returns the cycle weight in the low 8 bits (`kWeightMask`). Bit 29
marks a step boundary (the CALCULATOR freeze stops on it). Bit 30 marks a confirmed
hardware poll (a key or card-switch wait; not a printer BUSY wait, which is
counted in emulated cycles, so full speed speeds up printing). Bit 31 marks
a breakpoint: core breakpoints are set only by the headless tools, and the
loop just stops. An armed freeze that fires stops the batch, and the session
applies it before reporting it.

## Key Input Coordinate Systems

| Layer | Coordinates |
|---|---|
| Frontend hit test (`KeyboardLayout`) | Visual row 0–8, col 0–4 from the top left |
| `matrixCode(row, col)` (`KeyIds`) | `(row+1)×10 + (col+1)`, 11–95 — the codes KEYSTROKES uses |
| `keyIdAt(code)` (`KeyIds`) | the descriptor's key `(row−1)×5 + (col−1)`: a key ID (C59-1 AC-9) |
| `Machine::keyDown(keyId)` (`TIMachine`, `core/TIKeys.hpp`) | row → digit slot, column → K-line bit via `kTIKeyLineBits`; `key[digitSlot] \|= 1 << kbit` in the CPU |

`kTIKeyLineBits` maps column 1–5 to K-line bits `{1, 2, 3, 5, 6}` (index 0 unused);
bit 4 is the card-detect line. Scanning: `CoreArchitecture.md`
§ "Keyboard Matrix and Scanning".

## Physical Keyboard Mapping

Computer keyboards drive the calculator in the macOS Swift app, the Qt6 app
and the web client (`frontends/web/`, with its `keyboard` prop). iOS/iPadOS have no
keyboard input. The debugger and printer panels take no calculator
keys: Space (R/S vs. STEP) and Cmd/Ctrl+C (printer tape vs. selected text)
would have no single owner.

Values below are matrix codes. The website's keyboard legend
(`TI59_KEYBOARD_LEGEND` in `calc-u-site`'s `59/Pages.jsx`, prerendered without the engine)
lists the same bindings by hand.

### What is bound

**26 of the 45 keys, deliberately**: the white (digit) keys, the yellow keys
except 2nd, A–E, and EE / `(` / `)`. 2nd, INV, lnx, CE, LRN, x⇄t, x², √x, 1/x,
SST, STO, RCL, SUM, yˣ, BST, GTO, SBR, RST and R/S are pointer-only on
purpose. Do not "complete" the table without asking. With 2nd unbound, the
only second functions a keyboard reaches are A′–E′.

### Rules

1. A binding resolves to one or two matrix codes. 2nd functions are reached
   as on hardware: 2nd, then the key.
2. Shift + letter means "2nd, then that letter's key". Only `a`–`e` and
   `x` (×) are bound, so this gives A′–E′ and, with `x`, Deg.
3. Non-letters resolve on the character the keyboard produced, so Shift is
   not a 2nd prefix for them: `Shift+.` is `>` → EE. Lookup goes by produced
   character, never by scan code, so non-US layouts work wherever they put
   these characters.
4. With Command, Control or Option/Alt held, no key is the calculator's.

### The table

| Keyboard | TI key | Matrix | | Keyboard | TI key | Matrix |
|---|---|---|---|---|---|---|
| `0`–`9` | 0–9 | 92 82 83 84 72 73 74 62 63 64 | | `Escape` | CLR | 25 |
| `.` `,` | . | 93 | | `/` | ÷ | 55 |
| `<` | +/− | 94 | | `*` `x` | × | 65 |
| `a`–`e` | A–E | 11–15 | | `-` | − | 75 |
| `A`–`E` (Shift) | A′–E′ | 21 + 11–15 | | `+` | + | 85 |
| `>` | EE | 52 | | `=` `Return`/`Enter` | = | 95 |
| `(` `)` | ( ) | 53 54 | | | | |

Numeric-keypad keys produce the same characters and need no entries. `x` is
× as well as `*`, so a keyboard without a numpad needs no Shift for
multiplication.

### Injection timing

`key[]` is a wire level, not an event; the ROM accepts a key only when two
scans one display sweep apart see it, and drops a shorter press as bounce
(`ideas/KeypressLatch.md`). Every frontend uses `KeySequencer`:

- A press is held at least 100 ms. A key-up that comes sooner defers the
  release; it is never dropped. The web client sends on-screen clicks
  this way too, so a click shorter than that still registers.
- A tap waits for the steady scan loop before it presses, and again after it
  releases, so a key never lands in the ROM's release gate or debounce.
- One key at a time: a key-down while another is held releases the first.
- OS auto-repeat is ignored. A held key can never re-trigger, so repeats
  would only cause spurious releases.
- A two-code binding is one action played as two full taps; its key-up is
  ignored, because the ROM must see 2nd released and rescanned first.
- Losing focus releases the held key.

### Focus

Keys reach the calculator only while it has focus. It takes focus at launch
and on every click on the calculator. There is no focus indicator, so
clicking into the debug panel silently stops keys reaching the calculator.
This is a stepping stone: the Mac is meant to end up with one input surface
where every key has one meaning (`TODO.md` § UI). Panels that need keys
themselves (the CPU inspector's arrow keys) take focus on click, never on
appear. The web client is focusable (`tabIndex=0`, focused on
pointer-down with `preventScroll`) but not focused on load, so Tab still
works on the page.

## Card Reader Flow

The core side (TST BUSY wait, `CRD_READ`/`CRD_WRITE`, auto-eject at
`CRD_OFF`) is in `CoreArchitecture.md` § "Magnetic Card Reader". The
controller's side:

1. `fitCard(bytes, path, name)` decodes the file (`CardFile`, a `CardDocument`)
   and fits it into the cue card cutout, replacing the card there.
   `fitBlankCard(savePath, name)` fits a fresh version 2 card whose cue card is
   a Title with the file name (`freshCardCue`). Neither touches the reader.
   Each GUI's picker asks before a fresh card takes the name of an existing
   one: its first write replaces the file. Only the GUI knows its card folder.
2. `tapCard(nx, ny)` is a press on the canvas: `cardCornerAt` (`KeyboardLayout`)
   gives the side, and `feedSide(side)` puts it into the reader. GUIs call it on
   a press only, not on a drag. A press does nothing while a module's cue card
   covers the fitted card (`m_activeProgram > 0`).
3. The card state is `Swiping` until the core auto-ejects, and `litCardCorner()`
   gives the corner to draw lit (`cardCornerGeometry`, above the wash).
4. `tick()` sees the auto-eject and calls `ejectCard()`. A written bank goes to
   `writeFittedSide`: unless the card is fresh, it reads the file again
   (`TIFileAccess::readCard`), so a side changed elsewhere survives, merges the side
   and saves through `TIFileAccess::writeCard`. A file it can't read or parse is
   left alone and reported. A failed write leaves the fitted card as it was.

`refreshCueCard` shows `fittedCueCard()` when a card is fitted: its cue card, or
a Title for a card without one (never saved), with the corners' numbers from
the sides' headers (version 2) or `Banks:` (version 1). `resolveCueCard` still
lets a module's cue card cover it. A version 1 card has one side: either corner
feeds it, and a write stays version 1.

The fitted card goes with another fit, a reset, a model switch, a full preset
load, or a reload stage with its own cue card. The printer toggle and a module
change power-cycle the machine, so they remove it too (until C59-7, row 59-17).

Presets feed cards through the same path (`ArmCard:` / `InsertCard:`,
§ "State File Loading"); `TIFileAccess::cardFilePath(name)` resolves a card file
name in the frontend's card folder. `unreadable` from `TIFileAccess::readCard` means
the file exists but can't be read now, so no blank card goes in to overwrite it.

### Dropped Files

`dropAction(name)` says what a file dropped on the window does, by its name
and the model: a preset (`isStateFileName`) loads as from the Preset button; a
card (`isCardFileName`) is fitted on the TI-59 and ignored on the TI-58/58C.
`openDroppedFile(bytes, path, name)` does it. Nothing is fitted while a card is
in the reader. On the Mac, the file's security scope stays open while it is
fitted, because a write goes back to it.

Card file formats: `StateFileFormat.md` § "Card files".

## State File Loading

`TIAppPart::loadStateFile` writes the file's state straight into
RAM; only `KEYSTROKES:` simulates key presses. Section semantics and the
reference order: `StateFileFormat.md`.

1. UTF-8 check; `stateFileModel` (`MODEL:`); `parseStateFile` with the
   target model's limits. Parse errors are reported and the load continues.
2. `MODEL:` names another model → `startMachine(target)` first. Then the
   partition check (`stateFilePartitionError`) aborts the load.
3. `dropPresetCards`, stop the loop, unfreeze, and `applyState`
   (`StateApplier`). Then reset the heatmap baseline, start the loop, and
   apply the rest.
4. Persist `ti58c.mem`, then play `KEYSTROKES:`.

**Reloads and preset cards during playback** (`StateFileFormat.md` §
"Reloads", § "CARD"). The parser puts each reload stage and `CARD:` block
into the keystroke events (`shared_ptr`). This is the order of operations:

1. A `Reload` or `InsertCard` event waits for the scan loop like a key. It
   then calls a `KeySequencer::Host` hook (`EmulatorSession`), which raises
   the session's host-pending count.
2. The sequencer waits until that count drops.
3. A reload waits in the part's queue until after the call
   (`Listener::reloadRequested`). There
   `TIAppPart::applyReloadStage` halts the machine, runs `applyReload`
   (only the listed steps and registers)
   on the session's thread, lets it run again (unless frozen), and updates
   the cue card. It then calls `hostDone()`.
4. `ArmCard` and `InsertCard` queue their card in the session (`QueuedCard`).
5. On each 60 Hz `tick()` with an empty reader, `takeQueuedCard()` hands out
   the first card of the matching kind (the two kinds don't block each
   other):
   - an `InsertCard` card when the PC is in the scan loop;
   - an `ArmCard` card when the PC is in `ModelInfo::cardWait` and the core
     reports a card wait.
6. `feedQueuedCard` resolves the card:
   - a `mem:` card from its written bank, its `CARD:` block
     (`buildCardBank`, at the current partition), or blank;
   - a file through `TIFileAccess::cardFilePath` and `readCard`, fitted and fed at the side the
     directive names. A file card stays fitted afterwards; a `mem:` card takes
     a fitted card out and is never fitted itself.

   It inserts the card as a press on the card's corner would. On eject, a written bank
   goes to the memory card or to the file, and an `InsertCard` calls
   `hostDone()`.
7. `playbackFinished` clears the pending count. Queued cards stay until the
   next load, reset or model switch.

**Controls** (`PrinterTrace:`, `CutPaper:`, `DebugPanel:`, `Freeze:`,
`FreezeOnStart:`, `Step:`, `Resume:`) take the
same host-pending path. `Host::control` waits in the part's queue
until after the call (`Listener::controlRequested`), where `TIAppPart::applyControl` calls
what the GUI's button calls (`freeze`, `armPcChange`, `stepKeycode`, …), or
the `c59.show-debug-panel` topic for the tab, which is GUI state. While frozen, a
script's keys, reloads and inserted cards wait (`WaitingToPress` /
`WaitingToApply`); a keyboard tap still goes in at once.

Skipping the power-on routine leaves stale SCOM flags that confuse the
display and AOS.

## TI-58C Constant Memory

The TI-58C keeps its RAM through power-off. `TIAppPart` saves the
whole RAM and the user's cue card as `ti58c.mem` (`ConstantMemory`; format
in `DebugAPI.md`) through `TIFileAccess`, in the save folder the frontend
names (the Web's: the persistent file system, LIB-15 AC-20).

| When | What |
|---|---|
| Machine start | Power-on routine, then the saved RAM restored (`powerOn`), so startup code can't overwrite it |
| 0.5 s after a run-loop batch | Rewritten if its contents changed |
| Model switch, preset load, `suspend()` | Written at once if changed |
| Reset | `Machine::reset()`: the running machine keeps it (C59-1 OQ-6) |
| Clean reset | RAM zeroed, reset, written at once |

## ROM Loading

A frontend looks the ROM files up once at its start (LIB-12):
it calls `cu59::lookUpRoms` (`app/ProductRoms.hpp`; Qt6, the Swift bridge,
the Web's `bindings.cpp`), the library's `calcu::roms::lookUp` over the full
set of 24 files with the core's `TIRomReader`. Without the full set no app
session is made and the frontend shows `describe(missing)` (the Web as its
failed start, LIB-15 AC-3); there is no other ROM error. With it, every model switch and module change takes
its files from the `RomSet` in memory and reads no file. The catalogue's ROM
entries (`core/TICatalogue.cpp`) name each model's files: three ROM chips
(Datamath text dumps: header, a `---` line, then `AAAA: WWWW …` rows, words
masked to 13 bits) concatenated into 6144 words and two `*-CONST-K.txt`
files for the 64 constant rows.

| Model | ROM chips | Constants |
|---|---|---|
| TI-59 / TI-58 | `TMC0582.txt`, `TMC0583.txt`, `TMC0571B.txt` | `TMC0582-CONST-K.txt`, `TMC0583-CONST-K.txt` |
| TI-58C | `CD2400.txt`, `CD2401.txt`, `TMC0573.txt` | `CD2400-CONST-K.txt`, `CD2401-CONST-K.txt` |

The TI-59 image is checked against two sentinels: word 0 = `0x0A01`
(`CLR IDL`) and word 6143 = `0x1987`. A Solid State module's ROM is its
`roms/<ID>.rom.yaml` (`docs/formats/modules.md` §2, 5000 bytes, read by
`core/ModuleFile`). Since M-25 (C59-6 AC-8) the module list comes from the
14 module files (`allModuleMetadata(RomSet)`: `module-name`, `description`,
`menu-sort`); the cue cards still come from `roms/solid-state/cuecards.txt`
(until M-55).

## Places: the module and the PC-100C (C59-6)

The module and the PC-100C are peripherals in the machine's places `slot-1`
and `printer` (`reference/CoreArchitecture.md` § "Component Overview").
`EmulatorSession` builds its machine with them in the build request
(`MachinePeripherals`: the module ID, the printer, TRACE's position) and
changes them under the guard (`setModule`, `setPrinter`,
`printerControl`). `TIAppPart` owns what the app session keeps:
the module ID, whether the printer is connected, TRACE's position
(`m_printerTrace`: off at the start, never saved, kept across Reset, power
cycle, Cold boot, a model switch and a detach; C59-6 AC-6, row 59-25) and
the paper (`m_printerLines`, kept across a detach and a model switch,
AC-1). `changeModule`/`selectModule` and `setPrinterConnected` run the
change, then the power cycle that follows (row 59-11). Before a detach the
PC-100C ends the line it prints where the head is and hands its rows over
(EC-2). A state file applies `SOLID-STATE-MODULE:` and `PRINTER:` first and
then the state, whose start-up is the power cycle; TRACE is off after a
load unless its keystrokes set `PrinterTrace: on`. `FrameSampler` takes the
paper from the `c59.printer-output` capability when a PC-100C is plugged
in.

## Drawing Rules

All three GUIs draw with the same shapes and numbers; only the painting calls
differ.

### LED Display Rendering

- Glyphs: `SevenSegment` (`ledCell(i, glyph, level, calcOpacity)`, the glyph being `LedFrame::segments[i]` from the machine's display output:
  segments and opacity per cell, in cell 11 the "C" annunciator when it is
  brighter than the glyph there), never a
  font. Zero suppression happens in the core (`TMC0501`), which reports
  suppressed positions as not driven; `ledCell` blanks a position at
  level 0. All three renderers call it.
- Shapes: `LedGeometry` — hexagonal segments (modernized) or dot grids
  (classic), the decimal point, and per style the slant (bottom fixed; shear
  0.14, about 8°, modernized; 0.1139, about 6.5°, classic), colours and glow radii. The decimal point is not
  sheared.
- Brightness: `LedFrame` gives 0–255 per digit and decimal point
  (`DisplayPov`).
- Each frontend paints a blurred glow (and, modernized, a tighter bloom)
  under the crisp segments.

### Cue Card Rendering

Field grammar: `StateFileFormat.md` § "CUECARD: Field Grammar".

- **Templates.** `CueCard`, `MagnetCard` and `SolidStateCard`, each with its
  own artwork (`frontends/swift/App/Assets.xcassets`) and fractional layout
  (`cueCardLayout`). Only `SolidStateCard` has an ID and column dividers, and
  is printed gold (`0xC49223`); the others use the card's ink (black, pencil,
  sharpie). Only `MagnetCard` has bank badges.
- **Which card shows** (`resolveCueCard`): the running library program's
  card, else a generic card for the module, else the user's card (card file,
  preset, `ti58c.mem`).
- **Column spans** (`labelSpans`, `dividersBetween`). A grid row has 5
  cells. A `\blank` cell extends the preceding label's span; empty cells
  draw nothing.
- **Shrink-to-fit** (`cellFittingFontSize`). Each grid row gets one font
  size, the largest at which every span fits on one line (bold character
  width 0.64 × size), never below 40 % of the template's size. Free-text
  rows truncate instead.

The web client gets the card as a draw list `frontends/web/bindings.cpp` builds with
these functions for the size the page reports, and paints it on a canvas
(`frontends/web/src/painters.js`), badges included.

### Printer

`PrinterFont` holds the PC-100C 5×7 font and the paper geometry measured
from a real unit: dot pitch ≈ 0.430 mm, line heights including lines cut
short, and the copy-as-image scale (600 dpi, capped for long strips).
`PrinterGeometry::lineDots` turns a line cut short by the printer interrupt
(Core's `PrinterCodeLine`) into the dot rows drawn and, per row, the inked
and faint columns; `inkAlpha(heat)` gives a faint dot's ink (full from 20
heating cycles), `lineHeightUnits` the line's height on the strip. All three
renderers draw from these.

## Solid-State Program Display

The CALCULATOR tab's program view resolves where the running program comes
from with `programSourceFrom` (`ModuleImage`), which decodes the PRG SOURCE
flag as the firmware does (`CoreArchitecture.md` § "PRG SOURCE flag") plus
the CPU PC: bit 0 → `SolidState`; else bit 3 → `Rom`; 0 → `UserProgram`;
2 with the PC inside the RTN → LIB_RETURN window (ROM 1193–1194, 14F9–1506)
→ `SolidStateReturn`; any other 2, 4 or 6 → `FastMode`.

- `ModuleImage::parse` reads the module header into program ranges;
  `DebugModel` re-parses it when the machine or module changes.
- `ModuleImage::libraryStep()` maps the core's latched `libExecPC` (`0xFFFF`
  = none) to program, program-relative step (000 = the program's first
  keycode) and range. The program is cross-checked against SCOM[9] digits
  4/3 (mismatches go to the diagnostics).
- During `SolidStateReturn`, SCOM[0] nibbles 4–7 hold a raw CROM address,
  not a step. A listing is never built from it; the previous one is kept
  (`DebugModel::rebuildLive`).
- Colours: solid-state steps highlight blue; return levels with source 2
  show purple, like library levels (`DebugText`).

Snapshot fields and freeze semantics: `DebugAPI.md`.

## Tests and goldens

`tests/` (CTest target `CalcU59Tests`, run from the repo root) covers the
modules, with the ROMs from `roms/` (`LedGeometry` has no test of its own;
`BatchJitter` is covered through the cooperative runner). A second target,
`CalcU59TraceReader`, runs `tools/read_trace.py` on the trace the tests wrote
(`build/trace-test.bin`), so the reader stays in step with `TraceWriter`. Ports of Swift code are checked against
goldens produced by compiling the Swift original (`tools/goldens/`,
`tests/golden/`).
